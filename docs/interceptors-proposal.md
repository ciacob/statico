# Interceptors Support in Statico
## Architecture proposal

_Interceptors_ are a domain-agnostic functionality built into **Statico**. An interceptor's job is to receive arbitrary data and transparently transform it. The interceptors themselves are user provided, but the logic that powers and handles them is baked into Statico.

## The Anatomy of an Interceptor
An Interceptor is a subfolder that lives under `_interceptors`. That folder is generated by Statico, and is a sibling of `_resolvers`, `_templates`, etc. It comes with an `interceptors-info.md`, just like others do.

The name of an interceptor folder is irrelevant. Inside an interceptor folder there must be at least two files:
- `interceptor.json` (mandatory, defines the interceptor);
- `transformation.js` (mandatory Node.js module, the entry point for the interceptor's logic; complex interceptors can have several Node.js modules, and even assets, organized in subfolders).

The interceptor.json` has the following minimal structure:
```json
{
    "name": "my.namespace.my.name",
    "trigger" : {
        "type": "step|explicit",
        "stepType": "copy|resolve|output"
    }
}
```

Interceptors can be either triggered by one of the **known steps** — in which case the engine decides on their arguments and instruments their transformation (the actual transform logic remains in user control) — or **explicitly**, by any JSON outside the `_interceptors` folder — e.g., `build.json`, `commons.json`, etc.

One explicitly triggers an interceptor by providing its name and optionally one or more arguments, e.g.:
```json
{
    "en": {
        "interceptBy" : "ciacob.md",
        "@read-from": "text/bio-en.md",
        "@open-links-in-new-tab": "auto"
    }
}
```

The example depicts explicitly triggering a user-provided interceptor that consumes MD content and returns resulting. The value of the `en` node will be, at build time, the value returned by the interceptor.

N.B.: When an explicitly triggered interceptor returns a value, that value is inherited by the node that triggered the interceptor.

## The Step Interceptors Handlers

There are three available step interceptors handlers, one for each supported step type except `loop`. The engine scans and validates the `_interceptors` folder before attempting to build the site. Failure to validate the interceptor definitions aborts the build. Interceptors validation is also part of the `validate` built-in script. Discovered step interceptor definitions are handled by the engine as described below.

### 1. _Copy_ Interceptors
Their `transformation.js` is executed against each file that is about to be copied over. Full source and target file paths are received as arguments. 
The code is expected to either:
- output `true` — the file will be copied over as expected;
- output `false` — the file will be skipped;
- output `"path/to/alternate/source/file"` — the file will be transparently replaced with a changed variant.

### 2. _Resolve_ Interceptors
Their `transformation.js` is executed right before `ctx` is to be mutated. Both original `template` and the value about to be set into `ctx` are received as arguments. 
The code is expected to either:
- output `true` — the `ctx` will be mutated as expected;
- output `false` — the `ctx` will not be mutated;
- output `"alternate data to set"` — the `ctx` will be mutated with altered data instead.


### 3. _Output_ Interceptors
Their `transformation.js` is executed against file content that is about to be written to disk. File content and file path are received as arguments.
The code is expected to either:
- output `true`: the file write will proceed as expected;
- output `false`: the file write will be aborted;
- output `"alternate content to be written"` — the file write will proceed with alternate content.

## The `transformation.js` Core

At its core, the `transformation.js` of any interceptor must have a pure function with the following signature:
```javascript
/**
 * Entry point to execute the transformation of this interceptor. Does not
 * return a value. MUST BE IMPLEMENTED AS A PURE FUNCTION (must not depend
 * on, nor mutate outer context).
 * 
 * @param args Object of named arguments sent by the engine (for step-triggered
 *             interceptors) or the user (for explicit-triggered
 *             interceptors — same name minus the leading "@").
 * 
 * @param output Injected recipient to store transformation response into.
 *               The function is expected to set `output.response` to
 *               `true` (permit operation), `false` (deny operation),
 *               or to a value the original is to be substituted with.
 * 
 * @param tools Injected recipient with utility methods. Currently it only
 *              provides access to the onboard logging utility. Others may
 *              be added in the future.
 */
function transform (args, output, tools) {
}
```

## Interceptors Static Validation
If an `_interceptors` folder exist, all its subfolders must successfully validate as an interceptor:
- at least one `interceptor.json` and one `transformation.js`;
- with each `interceptor.json`:
  - `name` and `trigger` are given and have formally valid values;
  - `stepType` is required for `type=step`;
  - `name` is unique;
  - `name` is does not begin with `statico`;
- with each `transformation.js`:
  - a transform function must be publicly available.

If any JSON outside the `_interceptors` folder — e.g., `build.json`, `commons.json` — contains an `interceptBy` field in any of its nodes, the value of the `interceptBy` field must match one of the known interceptors `name`.

The scanning order is: first the `_interceptors` folder, then all JSON files outside of it. Node.js-specific JSON files, e.g., `package.json` will be skipped. If there is no `_interceptors` folder, no JSON is allowed to define `interceptBy`, anywhere.

## Running Interceptors
The engine will run interceptors defensively in protected code, and will fail the build for any falling interceptor, and log comprehensive context.
